# Default 세션을 Spec처럼 사용하는 워크플로 규칙

## 목차
1. 목적과 실현 범위
2. 적용 조건 (언제 켜고 끄는가)
3. 작업 전: 문답(Q&A) 절차
4. Spec 명명 및 폴더 생성 규칙
5. 작업 후: 산출물 문서(requirements / changes)
6. 실제 Spec 세션과의 관계 (충돌 방지)
7. 실행 체크리스트

## 1. 목적과 실현 범위

- 목적: default(Vibe) 세션에서도 Spec 세션처럼 "작업 전 문답 -> 작업 -> 산출물
  정리" 흐름을 따르게 한다.
- 실현 범위(중요): steering 규칙은 세션 타입 자체를 Vibe에서 Spec으로 **전환하지
  못한다.** 세션 타입은 IDE 레벨 선택이기 때문이다. 이 규칙은 default 세션이
  Spec처럼 **행동**하도록 만드는 행동 규약일 뿐이다.
- 따라서 이 규칙이 보장하는 것은 다음 두 가지다.
  1. 실질적인 작업(코드 변경 등)을 시작하기 전에 **문답으로 요구사항을 확정**한다.
  2. 작업 후 `.kiro/specs/{spec명}/`에 **요구사항과 적용내용 문서를 남긴다.**
- 이 규칙은 정식 Spec 워크플로(requirements/design/tasks 3단계, PBT 등)를
  대체하지 않는다. 가벼운 "문답 + 기록" 버전이다.

## 2. 적용 조건 (언제 켜고 끄는가)

이 워크플로는 **모든 질문에** 적용하지 않는다. 남발하면 단순 질의에도 문서가
생겨 오염된다. 아래 기준으로 판단한다.

### 적용한다 (ON)
- 소스 코드/설정 파일을 **실제로 변경**하는 작업.
- 여러 파일에 걸치거나, 동작/로직을 바꾸는 기능 추가·수정·리팩터링.
- 사용자가 "spec처럼", "문답하고 진행", "요구사항 정리해서"라고 요청한 경우.

### 적용하지 않는다 (OFF)
- 단순 질문·설명·조회(코드를 바꾸지 않는 Q&A).
- 오타 수정, 한 줄 변경 같은 사소하고 자명한 편집.
- 사용자가 "그냥 바로 해줘", "문서 만들지 마"라고 명시한 경우.

### 경계가 모호할 때
- 작업이 코드 변경을 수반하는지 우선 판단하고, 수반하면 ON을 기본값으로 한다.
- 사용자가 명시적으로 문서화를 원치 않으면 그 지시를 최우선한다.

## 3. 작업 전: 문답(Q&A) 절차

실질 작업을 시작하기 전에 요구사항을 문답으로 확정한다.

1. 요청을 분석해 **불명확한 점·전제·범위**를 정리한다.
2. 핵심 질문을 **한 번에 묶어** 제시한다(질문을 여러 턴으로 잘게 쪼개지 않는다).
   - 대상 파일/화면, 기대 동작, 예외 케이스, 보존해야 할 기존 동작, 범위 밖 항목.
3. 자명하게 유추 가능한 항목은 질문하지 말고 **"이렇게 가정하고 진행한다"**로
   제시해 확인만 받는다.
4. 사용자가 답하면 확정된 요구사항을 **짧게 재진술**하고 동의를 받은 뒤 작업한다.
5. 사용자가 "문답 생략하고 진행"을 원하면 즉시 작업으로 넘어가되, 작업 후 산출물
   문서에 **가정한 요구사항**을 기록한다.

> 목표는 "코드부터 고치기 전에 무엇을 왜 바꾸는지 합의"하는 것이다.

## 4. Spec 명명 및 폴더 생성 규칙

- 산출물은 `.kiro/specs/{spec명}/` 폴더에 모은다.
- `{spec명}` 규칙:
  - **kebab-case**(소문자 + 하이픈), 영문/숫자 위주로 간결하게.
  - 대상 화면/기능을 식별할 수 있게 작성. 예: `hp2302-part-dg-detail-popup`,
    `hp2203-booking-add-validation`.
  - 화면 ID가 있으면 접두어로 사용(예: `hp2302-...`)해 기존 spec 명명과 맞춘다.
- 문답 단계에서 spec명 후보를 **사용자에게 제시하고 확정**한다. 사용자가 지정하면
  그 이름을 그대로 쓴다.
- 이미 같은 작업의 spec 폴더가 있으면 새로 만들지 말고 **기존 폴더에 이어서** 문서를
  갱신한다.
- 폴더가 없으면 생성한다. 산출물은 최소 `requirements.md`, `changes.md` 두 개다.

## 5. 작업 후: 산출물 문서(requirements / changes)

작업 완료 후 `.kiro/specs/{spec명}/`에 아래 두 문서를 남긴다. 긴 문서는
`long-markdown-doc-rules`에 따라 골격 후 청크로 작성한다.

### 5-1. `requirements.md` (요구사항 + 문답 결과)

```markdown
# {제목} 요구사항

## 배경
- 왜 이 작업을 하는지, 대상 화면/파일.

## 문답 요약 (Q&A)
- Q1: ... / A1: ...
- Q2: ... / A2: ...
- (문답 생략 시) 가정한 요구사항: ...

## 요구사항
1. ...
2. ...

## 범위 밖 (Out of scope)
- ...
```

### 5-2. `changes.md` (적용 내용)

```markdown
# {제목} 적용 내용

## 변경 요약
- 한두 문장으로 무엇을 바꿨는지.

## 변경 파일
- `경로/파일1`: 변경 요지
- `경로/파일2`: 변경 요지

## 상세 변경 내용
- 함수/블록 단위로 무엇을 어떻게 바꿨는지.

## 검증
- 빌드/컴파일/테스트 수행 여부와 결과. 못 한 경우 그 사유.

## 남은 작업 / 후속
- 다음 단계나 미결 항목.
```

- 여러 번에 걸쳐 작업이 이어지면 `changes.md`에 **누적 기록**한다(날짜/차수 구분).
- 문서는 실제 적용한 내용과 일치해야 한다. 하지 않은 것을 했다고 적지 않는다.

## 6. 실제 Spec 세션과의 관계 (충돌 방지)

- 이미 정식 Spec 세션(오케스트레이터)으로 동작 중이면, 그 세션의
  requirements/design/tasks 워크플로가 우선한다. 이 규칙의 경량 문서(`changes.md`
  등)를 별도로 만들지 않는다.
- 이 규칙은 **default(Vibe) 세션 전용 경량 절차**다. 정식 Spec 문서 3종을
  강제하지 않으며, 필요하면 사용자가 정식 Spec 세션으로 승격하도록 안내한다.
- 기존 spec 폴더(예: `hp2302-part-dg-detail-popup`)에 정식 문서가 이미 있으면
  그 구조를 존중하고, 경량 `changes.md`를 덧붙이기보다 기존 문서 흐름을 따른다.

## 7. 실행 체크리스트

작업 유형이 "코드 변경"이면 아래를 순서대로 지킨다.

- [ ] 이 작업이 적용 조건(2절 ON)에 해당하는가
- [ ] 작업 전 핵심 질문을 묶어 문답하고 요구사항을 확정했는가
- [ ] spec명(kebab-case)을 정하고 사용자와 합의했는가
- [ ] `.kiro/specs/{spec명}/` 폴더를 확인/생성했는가
- [ ] 작업 후 `requirements.md`(요구사항 + 문답)를 작성했는가
- [ ] 작업 후 `changes.md`(변경 파일 + 상세 + 검증)를 작성했는가
- [ ] 문서 내용이 실제 적용 내용과 일치하는가
- [ ] 정식 Spec 세션이면 그쪽 워크플로를 우선했는가(6절)
